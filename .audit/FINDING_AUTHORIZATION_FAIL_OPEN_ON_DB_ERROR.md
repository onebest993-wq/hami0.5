# الإذن كان يُفتح عند فشل الاستعلام لا عند نجاحه

**التاريخ:** ٩ آب ٢٠٢٦
**الخطورة:** عالية — تجاوز إبطال الحساب
**الحالة:** مُصلَح ومُبرهَن

---

## ١. ما وجدناه

`getVerifiedTokenSubject` تُصادق التوكن على خدمة Supabase، ثم تُجري فحصاً حيّاً
على قاعدة البيانات لتمنع فجوة الإبطال: هل ما يزال هذا المستخدم مسموحاً له؟

```ts
const isActive = await isUserActiveLive(userId);
if (!isActive) return null;
```

و`isUserActiveLive` تسأل `profiles` ثم `lawyers`. لكن قارئ الصفّ كان يُعيد `null`
لحالتين مختلفتين تماماً:

```ts
if (error) return null;   // الاستعلام فشل
return data;              // نجح ولم يجد → null أيضاً
```

فحين يفشل الاستعلام تُقرأ النتيجة على أنها «مستخدم جديد بلا ملفّ بعد»:

```ts
writeCachedUserStatus(userId, true);
return true;
```

**عطل عابر واحد في قاعدة البيانات كان يكفي لتحويل محامٍ محظور أو محذوف إلى
مستخدم مُصرَّح له.** والإذن يُخزَّن خمس دقائق (`USER_STATUS_CACHE_TTL_MS`)، فتُمدَّد
النافذة إلى ما بعد انقضاء العطل نفسه.

## ٢. لماذا كان قابلاً للاستغلال

الشرط ليس نظرياً: `fetchSingleUserRow` تُعيد `null` أيضاً حين لا يوجد عميل إدارة
(`SUPABASE_SERVICE_ROLE_KEY` غائب أو مُدوَّر)، وحين ترمي الشبكة، وحين تُغيَّر سياسة
RLS على الجدول. كل واحدة من هذه تفتح الباب بلا أثر في السجلّ.

## ٣. الإصلاح

ثلاث حالات لا حالتان:

```ts
type UserRowLookup =
  | { kind: 'row'; row: Record<string, unknown> }
  | { kind: 'absent' }        // الاستعلام نجح ولم يجد
  | { kind: 'unavailable' };  // تعذّر السؤال
```

والقرار بعدها:

| الحالة | الحكم |
|---|---|
| وُجد صفّ في أيّ من الجدولين | يُقرأ الصفّ ويُخزَّن الحكم |
| نجح الاستعلامان ولم يجدا | إذن — تسجيل جديد لم يُكتب صفّه بعد (السلوك الأصلي محفوظ) |
| تعذّر أحدهما | **منع في الإنتاج، بلا تخزين** |

عدم التخزين مقصود: الطلب التالي يسأل من جديد بدل تجميد تخمين خمس دقائق. وأثر
العطل العابر يصير ٤٠١ قصيرة يُعاد منها المحاولة، لا نافذة دخول لحساب مُبطَل.

`!isProductionNodeEnv()` يُبقي بيئة التطوير سالكة بلا قاعدة بيانات.

## ٤. البرهان

`wifeValidatorUserStatus.test.ts` — ستّ حالات تفصل الأمرين:

- فشل الاستعلام → `null` (كان يُعيد المشترك)
- تعذّر بناء عميل الإدارة → `null`
- حكم المنع لا يُخزَّن: الطلب التالي بعد شفاء القاعدة يمرّ
- استعلام نجح ولم يجد → إذن (لا نكسر تسجيل جديد)
- محظور يُقرأ صفّه فعلاً → منع
- نشط → إذن

الثلاث الأولى تسقط على الكود القديم.

## ٥. تنظيف مصاحب

كان في `wifeValidator.ts` عميل إدارة Supabase ثانٍ خاص به، يُخزَّن مرّة واحدة
بلا بصمة على المفتاح — فيبقى العميل القديم حيّاً بعد تدوير المفتاح. استُبدل
بالعميل المُخزَّن المشترك (`supabaseAdminClient.ts`) الذي يربط الذاكرة بالعنوان
والمفتاح معاً.

## ٦. الحدود

الفحص يبقى معتمداً على وجود صفّ في `profiles` أو `lawyers`. حساب مُبطَل بحذف
صفّه من الجدولين معاً — لا بوسمه محظوراً — يُقرأ «تسجيل جديد» ويُؤذن له. سدّ هذا
يحتاج قائمة إبطال صريحة (`revoked_subjects`) لا استنتاجاً من غياب الصفّ، وهو
قرار مخطّط بيانات خارج نطاق هذه الجولة.
