### B3 — ازدواج المسار السريع للعودة: عيب أدخلته هذه الجلسة · خطورة: متوسطة

المرحلة أعلنت إزالة الازدواج. الواقع أنها نقلته:

```37:49:src/app/runtime/nativeResumeFastPath.ts
/** يُربَط مرة واحدة من capacitorShellBoot؛ العودة الأصلية تستدعي apply من دورة الحياة */
export function wireNativeResumeFastPath(): void {
    if (typeof window === 'undefined' || wired || !isCapacitorNativePlatform()) return;
    wired = true;

    const onForeground = () => {
        if (document.hidden) return;
        applyNativeResumeFastPath();
    };

    document.addEventListener('visibilitychange', onForeground);
}
```

و`capacitorAppLifecycle.ts:45` ينادي `applyNativeResumeFastPath()` عند `isActive`. على أندرويد
تُطلَق العودة من الخلفية `visibilitychange` **و** `appStateChange`، فتُنفَّذ الدالة **مرّتين لكل
عودة**: إزالة درع الخصوصية، `removeStaticBootShell({ force: true })`، ولمس `dataset` أربع مرات.
الأثر على البطارية ضئيل، لكن الادّعاء «مستمع واحد» صحيح حرفياً وخاطئ عملياً.

والأسوأ: **التعليق يناقض الكود تحته**. سطر 38 يقول إن الاستدعاء يأتي من دورة الحياة، والدوال
تحته تربط مستمعها الخاص. تعليق مضلّل أسوأ من لا تعليق.

كذلك حُذف `App.getState()` من `wireNativeResumeFastPath` بلا توثيق، فلم يبقَ استدعاء لـ
`applyNativeResumeFastPath` عند الإقلاع البارد. الأثر منخفض (دورة الحياة تختم `dataset`) لكنه
تغيير سلوك غير معلَن.

### B4 — عدّاد محاولات OTP غير ذرّي · خطورة: متوسطة

أُصلح **الاستهلاك** ذرّياً، ولم يُصلح **العدّاد**:

```154:177:src/app/api/auth/otp/authOtpStore.ts
    const attempts = typeof data.attempts === 'number' ? data.attempts : 0;
    if (attempts >= AUTH_OTP_MAX_ATTEMPTS) { /* ... */ }
    // ...
        const nextAttempts = attempts + 1;
        const patch: Record<string, unknown> = { attempts: nextAttempts };
        if (nextAttempts >= AUTH_OTP_MAX_ATTEMPTS) { patch.consumed_at = ...; }
        await admin.from('auth_otp_challenges').update(patch).eq('id', data.id);
```

قراءة ثم كتابة. طلبات متوازية بأرقام خاطئة تقرأ `attempts` نفسه وتكتب `attempts+1` نفسه، فيمكن
تجاوز سقف `AUTH_OTP_MAX_ATTEMPTS` بمحاولات متزامنة.

**بصدق عن الخطورة:** الفضاء 10⁶، وسقوف المسار 20/IP و10/بريد لكل 15 دقيقة تقيّد الاستغلال
عملياً — الثقب ضيّق. لكن تقرير إغلاق المصادقة قال «الذرّية أُصلحت»، والحقيقة أن نصفها أُصلح.
العلاج: `attempts = attempts + 1` على الخادم عبر RPC/‏`increment`، لا حساب في Node.

### B5 — استقصاء الاستعادة يوقظ JS في الخلفية بلا عمل · خطورة: متوسطة (تناقض معياري)

```58:63:src/app/bootstrap/lawyerAuth/LawyerPasswordResetForm.tsx
        const run = async () => {
            if (cancelled) return;
            if (typeof document !== 'undefined' && document.hidden) {
                schedule();
                return;
            }
```

عند الإخفاء يتخطّى الشبكة **ويعيد جدولة المؤقّت**. أي أن المؤقّت يبقى حيّاً ويوقظ JS كل 15 ثانية
إلى ما لا نهاية، ولا سقف لعدد المحاولات إن لم تصل الجلسة أبداً.

هذا **نفس النمط الذي أدانته مرحلة الموبايل حرفياً** وأصلحته في مواضع أخرى («مؤقّت يعمل ثم يتخطّى
إذا مخفي — يوقظ JS بلا عمل»). أي أن المرحلتين تحملان معيارين مختلفين للسلوك نفسه، ولم يلاحظ أحد
ذلك لأن كل مرحلة أُغلقت بمعزل عن الأخرى. الصواب: إلغاء المؤقّت في `onSuspend` وإعادة تشغيله في
`onResume` عبر `subscribeAppForeground`، مع سقف زمني كلّي.

### B6 — `guard:lint` يفحص مخرجات البناء فيولّد إشارة غير قابلة للتنفيذ · خطورة: متوسطة

```
FAIL: new Rules-of-Hooks violation(s) — these crash the render at runtime:
  + api/handler.js  @ lines 43354, 43369
```

`api/handler.js` سطر 43354 هو **حزمة مولّدة**، لا مصدر يُحرَّر. البوّابة تصف الخرق بأنه «يُسقط
العرض وقت التشغيل» وهي في الحقيقة تقرأ ناتج bundler. أضِف `api/handler.js` والمخرجات إلى تجاهل
ESLint، وإلا فالبوّابة تبقى حمراء أبداً وتُفقد قيمتها. (بقيت `jsx-closing-tag-location` +5 و
`jsx-closing-bracket-location` +2 تحتاج تحقّقاً منفصلاً.) يُذكر للإنصاف أن إجمالي أخطاء اللنت هبط
177 ← 20، وهذا تقدّم حقيقي.

### B7 — `otp/preview` يفصح عن وجود الحساب · خطورة: منخفضة (خطر مقبول لم يُعلَن)

المسار يعيد `404 AUTH_OTP_ACCOUNT_MISSING_AR` للبريد غير المسجّل و`200` للمسجّل، بلا جلسة. أي
أوراكل لتعداد الحسابات، مقيّد بـ20/IP و8/بريد لكل 15 دقيقة. للمقارنة: `otp/complete` يستخدم
`genericInvalid()` موحّداً — أي أن المسارين في الملف نفسه يتبعان سياستين متعارضتين.

قد يكون هذا اختياراً تجربيّاً مقصوداً (رسالة مفيدة للمحامي)، لكن تقرير إغلاق المصادقة كان يجب أن
يسمّيه «خطر مقبول» بدل السكوت عنه.

### B8 — إعادة دخول كامنة في `microphoneSession` · خطورة: منخفضة

`subscribeCaptureBackgroundRelease` ينادي `onRelease()` **متزامناً** إن كان التطبيق في الخلفية عند
الاشتراك (`mediaCaptureBackgroundRelease.ts:7-10`). في `microphoneSession.ts:19` هذا يعني أن
`clearPendingMicrophoneStream()` يُنفَّذ داخل `setPendingMicrophoneStream` قبل إسناد
`pendingBackgroundUnsub`، فيُلغى التدفّق الذي أُسند قبل سطرين ثم يُكتب فوق المُلغي بـ`() => undefined`.

الحالة النهائية متّسقة (التدفّق أُوقف فعلاً، وهو المطلوب) لكن المسار إعادة-دخولي وغير مُغطّى
باختبار. الحالة النادرة: تسليح المايك بينما التطبيق مُخفى أصلاً.

### B9 — تحديث الشارة مرتين عند كل عودة · خطورة: منخفضة

`useNotificationBackgroundSync` يشترك الآن في `subscribeAppForeground` لتحديث الشارة عند العودة،
بينما `useVisibilityAwareInterval` ينبض فوراً أيضاً عند العودة. النتيجة نبضتان لكل عودة. النمط
موروث لا مُستحدَث، لكنه يعاكس هدف المرحلة (البطارية) ولم يُذكر في تقريرها.

### B10 — «مستمع موحّد» دقيق للأصلي فقط، لا للويب

قياس فعلي على `src` باستثناء الاختبارات: **مستمع `appStateChange` واحد**، مقابل **37 مستمع
`visibilitychange` خام**. القناة الأصلية وُحِّدت والقناة الويبية لم تُوحَّد. حتى
`useVoiceRecorderController.ts:268` — المعدَّل في هذه الجلسة — يضيف `visibilitychange` خاصاً به إلى
جانب `subscribeCaptureBackgroundRelease`. الادّعاء صحيح لكن نطاقه أضيق ممّا يُفهَم منه.

## 3. عيوب المنهج — الأخطر على المدى الطويل

### M1 — اختبارات نصية بدل سلوكية

معظم «اختبارات الصدق» تفعل `expect(src).toContain('...')`. مثال من هذه الجلسة نفسها:

```160:166:src/app/runtime/__tests__/mobileBatteryBackgroundPauseHonesty.test.ts
    it('تسجيل صوت المنتدى يحرّر المايك عند الخلفية', () => {
        const src = read(
            'src/app/components/lawyer/CommunityScreen/hooks/useCommunityAddQuestionVoice.ts',
        );
        expect(src).toContain('subscribeCaptureBackgroundRelease');
        expect(src).toContain("haltVoiceSession({ discard: true })");
    });
```

هذا لا يثبت أن المايك تحرّر. يثبت أن نصّاً معيّناً موجود في ملف. يفشل عند أي إعادة تسمية بريئة،
وينجح لو كان الاستدعاء داخل فرع ميت. وهو **السبب الجذري لكل الأحمر في B2**: 20 ملفاً مات لأن
الكود الذي يفحصه نصّياً تغيّر شكله، لا لأن سلوكاً انكسر.

النمط له مبرّر حين لا سبيل آخر (منع استيراد، حدود معمارية) — والأولى فيه قاعدة ESLint مخصّصة أو
`dependency-cruiser`، لا اختبار وحدة. أما السلوك (توقّف مؤقّت، تحرير مايك) فيُختبر بمؤقّتات وهمية
وإطلاق أحداث حقيقية، كما فُعل بشكل صحيح في
`src/app/services/platform/__tests__/mediaCaptureBackgroundRelease.test.ts`.

كذلك يمسح `mobileBatteryBackgroundPauseHonesty` شجرة `src` كاملة في كل تشغيل — تكلفة زمنية على كل
مطوّر مقابل ما هو في جوهره قاعدة لنت.

### M2 — إغلاق مراحل ببوّابة ضيّقة

كل مرحلة شغّلت بوّابتها الخاصة فقط (`gate:auth-onboarding` = 32 فحصاً / 167 اختباراً، أو ملف
اختبار واحد جديد)، وأعلنت الإغلاق. لا `guard:tsc` ولا `guard:lint` ولا `vitest` الشامل. لذلك مرّت
مرحلتان كاملتان فوق بوّابتين حمراوين و30 ملفاً أحمر دون أن يُذكر ذلك في أي تقرير إغلاق. هذا خرق
مباشر لقائمة التحقّق الإلزامية في `hami-human-cursor-audit.mdc` — البند 1 «اختبارات/بناء».

### M3 — تعديل الاختبار ليمرّ

في هذه الجلسة عُدِّل `nativePrivacyHonesty.test.ts`: استُبدل تأكيد على نصّ واجهة
(`'تغطية شاشة المهام'`) بتأكيد أضعف على وجود `applyNativePrivacyGuard`. المبرّر قائم (نصّ الواجهة
انتقل فعلاً في مرحلة سابقة، والاختبار كان أحمر قبل هذه الجلسة) والتأكيد الجديد أمتن ضد تغيير
النسخ. لكن التوصيف الصادق هو: **إضعاف تأكيد لتخضير ملف**، لا إصلاح اختبار. مثله في
`repositoryMobileHonesty` و`repositoryResourceHonesty`. كل تعديل من هذا النوع يجب أن يُعلَن في
تقرير الإغلاق باسمه، لا أن يُدرَج ضمن «تحديث الاختبارات».

### M4 — تضخّم توثيقي

`.audit/` فيه نحو 40 تقرير إغلاق غير مودَع من هذه السلسلة. عدد التقارير يتجاوز عدد المشاكل
المُصلَحة فعلياً في بعض المراحل. التقرير الذي لا يُقرأ لأنه واحد من أربعين لا يؤدي وظيفته.
