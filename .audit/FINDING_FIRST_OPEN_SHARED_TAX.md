## ١) الجواب المختصر

ثلاث حقائق مقيسة، مرتّبة بحسب الأهمية:

1. **نواة الإقلاع سليمة وممتازة.** `main.js` يحتاج 11 وحدة / 306 ك.ب فقط. لا خطأ في النواة ولا في مسار الإقلاع.
2. **المشروع كبير فعلاً** — 576,428 سطر مصدر في 5,809 ملفاً. تقدير «الحجم ليس كبيراً» غير دقيق.
3. **الخلل الحقيقي:** كل قسم يدفع **ضريبة ساكنة مشتركة ~1.8 م.ب** لا يستعمل أكثرها. أول قسم يُفتح في الجلسة يدفعها وحده، فيبدو بطيئاً، وما بعده يبدو سريعاً. السبب **تشكيل الحزم** (Rollup/`manualChunks`) لا منطق التطبيق.

**سوء برمجة؟** لا — لا في النواة ولا في منطق الأقسام. الخلل في **غياب حدود الوحدات** + إعداد بناء يعالج العَرَض.

## ٥) الدليل القاطع — 17 سطراً تكلّف 1,240 ك.ب

`LawyerAuthOtpPanel` تستورد **رمزاً واحداً فقط** من حزمة خط أنابيب التنفيذ:

```js
import{j as G}from"./execution-dashboard-persist-pipeline-DJHuKBWZ.js";
```

ذلك الرمز هو `parseJsonResponse` من `src/app/utils/bffJsonResponse.ts` — دالة من 17 سطراً، صفر اعتماديات، تعليقها نفسه يقول «ورقة بلا اعتماديات»:

```ts
export async function parseJsonResponse<T>(response: Response): Promise<T> {
    const text = await response.text().catch(() => '');
    try { return JSON.parse(text) as T; } catch { return {} as T; }
}
```

سلسلة السحب المقيسة من `dist`:

```
LawyerAuthOtpPanel < execution-dashboard-persist-pipeline               225 KB
                   < execution-dashboard-boot-pipeline                  260 KB
                   < supabase-browser-client < vendor-supabase          197 KB
                   < lawyer-home-paint                                  118 KB
                   < execution-dashboard-workspace-pipeline               73 KB
                   < lawsuit-archive-grid                                 58 KB
                   < lawsuit-archive-grid < archive-portal-lite           47 KB
                   < lawsuit-archive-grid < vendor-misc                   67 KB
                   < lawyer-home-hub-card                                 45 KB
                   < lawyer-lawsuit-lite                                  36 KB
                   < archive-execution-cards                              34 KB
                   < execution-handler-cluster-runtime                    28 KB
                   ──────────────────────────────────────────────────────────
                                                                    ≈ 1,240 KB
```

**استيراد `JSON.parse` يكلّف 1.24 م.ب.**

### السبب الميكانيكي

`bffJsonResponse` **غير مذكور في `manualChunks` إطلاقاً** (تحقّقت: صفر تطابق في `vite.config.mts`). فتُرك لخوارزمية Rollup، التي أسكنته داخل حزمة مسمّاة يدوياً بحجم 225 ك.ب تعتمد ساكناً على نصف التطبيق.

نفس النمط في موضع آخر: `src/app/runtime/appStateEvents.ts` — 11 سطراً، ثابت اسم حدث ودالة `dispatchEvent` — سكن داخل حزمة `lawyer-dashboard-canvas`. ويصل إليه `useVisibilityAwareInterval` الذي تستعمله لوحة الـ OTP.

`experimentalMinChunkSize: 0` مضبوط أصلاً، فدمج micro-chunks ليس السبب. السبب أن الأوراق المشتركة غير المسمّاة تُترك لخوارزمية تضعها في أسوأ مكان.

## ١٠) الحدود — ما لم يُنفَّذ ولم يُتحقَّق منه

- **لم يُعدَّل أي سطر كود أو إعداد بناء.** بطلب المستخدم: تقرير فقط.
- **لم يُبنَ المشروع للتحقق من أن أي إصلاح يعطي الرقم المتوقع.** كل الأرقام من `dist` الموجود.
- **لم يُقس زمن** الفرق قبل/بعد لأي إصلاح مقترح. تقارير `.audit` السابقة سجّلت درساً صحيحاً: **خفض الإغلاق الساكن لا يُترجَم دائماً إلى زمن أقل** (`FINDING_BOOT_IS_SLOW.md` §٥: محاولة تأجيل `SparkCalendarNudgeHost` خفّضت الإغلاق 648 ك.ب ورفعت الزمن من 9,489 إلى 11,210 م.ث). أي إصلاح يجب أن يُقاس بـ `perf:boot-ttfi` قبل/بعد.
- **لم أجرد كل الأوراق المسجونة** داخل حزم كبيرة — أثبتُ حالتين (`bffJsonResponse`، `appStateEvents`) ورجّحت وجود غيرها بلا حصر.
- **لم أفحص** هل بعض الـ 759 ك.ب (حزم الأرشيف تحديداً) مطلوب فعلاً للمنتدى عبر ربط قضية. `execution-dashboard-persist-pipeline` عبر `parseJsonResponse` عارض بلا شك؛ حزم الأرشيف لم تُتبَع حافةً بحافة.
- **لم يُفحص الأمان ولا الموبايل ولا RTL** في هذه الجولة — الدرجات أعلاه لهذين البُعدين موروثة لا مُتحقَّقة.

## ١١) الموقع

**هذه المرحلة ليست مغلقة كإصلاح** — هي مغلقة كتشخيص فقط.

**تحديث ٣١ آب:** الإصلاح الآمن نُفِّذ وقِيس في `.audit/PHASE_FIRST_OPEN_SHARED_TAX_CLOSURE.md`. OTP 1٬830 → 387 ك.ب. المنتدى ما زال يسحب persist.

جاهز للانتقال إلى إصلاح: **نعم**، والمسار المقترح مرتّباً بالوفر المتوقع:

1. **عزل الأوراق المشتركة** — تسمية `bffJsonResponse` و`appStateEvents` وأشباههما حزماً مستقلة في `manualChunks`. أرخص تغيير، وأعلى وفر متوقع (~700 ك.ب من أول فتح). **يجب أن يُقاس، لا يُفترض.**
2. **جرد كامل** للأوراق الصغيرة المسجونة داخل حزم > 100 ك.ب.
3. **قطع الحواف من المصدر** لا من إعداد البناء — حدّ معماري يمنع ملف مصادقة من مشاركة حزمة مع لوحة التنفيذ (مثلاً قاعدة ESLint على حدود المجلدات).
